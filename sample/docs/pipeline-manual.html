Microservices CI/CD Pipeline

A production-ready, reusable GitHub Actions pipeline for containerized Python microservices — from code commit to multi-environment deployment.

Section 01 — Overview & Architecture

What Does This Pipeline Do?

Instead of duplicating 50+ lines of CI/CD YAML per microservice, this repository uses a Reusable Workflow pattern — a shared pipeline template that any service can call with custom inputs. Think of it as a parameterized function for software delivery.

🔁
Reusable Workflow
One shared reusable-pipeline.yml template serves all microservices via parameterized inputs.
⚡
Parallel Pipelines
All services run their CI/CD pipelines simultaneously on every push, cutting total wait time significantly.
🐳
Docker-Native
Every service is built, smoke-tested, vulnerability-scanned, and published to GHCR as an OCI image.
🛡
Quality Gates
Lint · 100% test pass · configurable coverage threshold · Trivy security scan — all must pass before publish.
🛆
Dual CD Modes
Continuous Deployment (zero-touch) and Continuous Delivery (staging + manual approval gate) — per service.
📦
Dual-Tag Publishing
Every release is tagged :latest AND :<git-sha> for instant rollback and a full audit trail.
End-to-End Flow
💾 Git Push main / PR
🧪 Lint & Test Ruff · Pytest
🐳 Build & Verify Docker · Smoke
🔍 Security Scan Trivy CVE audit
📦 Publish GHCR :latest · :sha
AUTO
🚀 Production Continuous Deployment
GATED
🎭 Staging Continuous Delivery
ℹ️ On Pull Requests, only the Lint & Test and Build & Verify stages run. The image is never published to GHCR on unmerged PRs — preventing registry pollution.

Section 02 — Pipeline Stages

Stage Breakdown

Every service call to reusable-pipeline.yml executes the following sequential job chain. Each job must succeed before the next begins.

01
🧪 Lint, Test & Coverage Job: test

Enforces code quality, correctness, and test coverage before any container is ever built. Runs in a fresh ubuntu-latest environment with pip dependency caching.

Checkout code — fetches the repository at the triggering commit SHA.
Setup Python — provisions the exact Python version specified in inputs (3.11 by default). Pip packages are cached using pyproject.toml as the cache key.
Install dependencies — upgrades pip and installs Ruff (linter) plus all service requirements.
Lint with Ruff — scans for syntax errors, PEP 8 violations, unused imports, and import ordering. Fails fast if any issue is found.
Run Pytest + Coverage — all tests must pass. Coverage below min-coverage (80% or 85%) blocks the Docker build entirely.
Upload HTML coverage report — detailed htmlcov/ uploaded as a downloadable workflow artifact named coverage-report-{image-name}.
# Command that runs in the service working directory
pytest tests/ \
  --import-mode=importlib \
  --cov=app \
  --cov-report=term-missing \
  --cov-report=html:htmlcov \
  --cov-fail-under=80   # (or 85 for order_service)
02
🐳 Build, Verify & Publish Container Job: docker-build

Assembles the OCI-compliant Docker image, verifies it runs via an automated smoke test, scans for CVEs, then publishes to GHCR with dual tags. Only starts if Stage 01 passes (needs: test).

Set up Docker Buildx — enables multi-platform build support.
Build Docker image — runs docker build -t {image-name}:latest . using python:3.11-slim as base.
Smoke Test — starts the container in background, waits 3 seconds, issues an HTTP GET to the health endpoint. A non-200 response or crash fails the pipeline.
Trivy security scan — audits image layers for CRITICAL and HIGH CVEs. Runs in audit mode (reports without blocking).
Login to GHCR — authenticates using built-in GITHUB_TOKEN (only on main branch or release events).
Tag & Push to GHCR — publishes :latest (rolling) and :{git-sha} (immutable) tags. Owner is auto-lowercased for OCI compliance.
# Smoke Test sequence
docker run -d --name test-container \
  -p {app-port}:{app-port} {image-name}:latest
sleep 3
curl --fail http://localhost:{app-port}{health-endpoint}
docker stop test-container && docker rm test-container

# Dual-tag publish
IMAGE_URI="ghcr.io/${OWNER_LOWER}/{image-name}"
docker tag {image-name}:latest ${IMAGE_URI}:latest
docker tag {image-name}:latest ${IMAGE_URI}:{github.sha}
docker push ${IMAGE_URI}:latest
docker push ${IMAGE_URI}:{github.sha}
3A
🚀 Continuous Deployment — Direct Production Rollout Job: deploy-production-automated

Activated when deployment-type: "deployment" (used by Learning Service). Once the image is in GHCR, it rolls directly to production with zero human intervention.

Pulls the exact commit-SHA-tagged image from GHCR.
Deploys to the production-automated GitHub Environment.
Verifies the production container responds on its health route.
Pipeline completes with Completed status — no human approval required.
✅ Best for: fast-moving APIs, internal tools, learning systems where speed of iteration outweighs manual oversight.
3B
🎭 Continuous Delivery — Staging + Manual Approval Gate Jobs: deploy-staging → deploy-production-gated

Activated when deployment-type: "delivery" (used by Order Service). The artifact is automatically staged for QA verification, then a manual approval gate blocks production rollout until an authorized reviewer approves.

Auto-deploy to Staging — pulls the SHA-tagged image and deploys to the staging GitHub Environment with health verification.
Pause at Approval Gate — the pipeline enters Waiting for review state at the production-manual-gate environment. Authorized reviewers are notified.
Manual approval — a reviewer logs into GitHub Actions, inspects staging, and clicks Approve and deploy.
Production deploy — upon approval the pipeline resumes, deploying the same SHA-pinned image to production with health verification.
⚠️ Best for: financial services, order processing, billing — any system requiring human business sign-off before reaching end users.

Why Each Service Has Its Own pytest.ini

In a monorepo, pytest's discovery mechanism can accidentally pick up tests from sibling services. Each service carries its own pytest.ini to prevent this: 

[pytest]
pythonpath = .          # Prevents ModuleNotFoundError: No module named 'app'
testpaths  = tests       # Restricts discovery to THIS service's test folder only
addopts    = --import-mode=importlib  # Isolated imports - prevents name collisions
Section 04 — Reusable Workflow Inputs

Inputs Reference Table

All parameters accepted by reusable-pipeline.yml via workflow_call. Any microservice added to ci.yml can override these defaults.

Input Type Default Required Description
working-directory string "." No Path to the service folder containing Dockerfile and pyproject.toml. Example: services/order_service
python-version string "3.11" No Python runtime version to provision on the CI runner. Passed to actions/setup-python@v5.
min-coverage number 80 No Minimum code coverage percentage (0–100) required for the test job to pass. Passed to --cov-fail-under.
image-name string "app" No Docker image tag name used locally and as the GHCR repository name. Must be lowercase. Example: order-service
app-port number 8000 No Port the container exposes and listens on. Used in docker run -p, the smoke test curl, and environment URLs.
health-endpoint string "/health" No HTTP route used to verify the container is alive during smoke test and deploy verification. Must return HTTP 200.
push-image boolean true No Whether to publish the Docker image to GHCR. Only takes effect on main branch pushes or release events.
deployment-type string "deployment" No CD strategy after image publish:
"deployment" — 100% automated direct-to-production rollout.
"delivery" — auto staging deploy + manual approval gate for production.
💡
Adding a new microservice takes ~3 minutes. Create the service folder, add the required files, then add one job block to ci.yml: 
payment-service-ci:
  name: "Project 3: Payment Service"
  uses: ./.github/workflows/reusable-pipeline.yml
  with:
    working-directory: "services/payment_service"
    python-version:    "3.11"
    min-coverage:     80
    image-name:       "payment-service"
    app-port:         9000
    health-endpoint:  "/health"
    deployment-type:  "delivery"
Section 05 — Operator Runbook

Pulling & Running Images from GHCR

Once the pipeline publishes an image, any developer or platform engineer can pull and run it locally or on a remote host. Follow the steps below in order.

1
Authenticate to GitHub Container Registry (one-time setup)
Generate a GitHub Personal Access Token (PAT) with the read:packages scope at: GitHub → Settings → Developer settings → Personal access tokens.
docker login ghcr.io -u YOUR_GITHUB_USERNAME
# When prompted for Password, paste your PAT (not your GitHub password)
⚠️ Store the PAT securely. Do not commit it to source control.
2
Pull the latest image
Replace <owner> with the GitHub username or organization (always lowercase).
# Learning Service (port 8000)
docker pull ghcr.io/<owner>/learning-service:latest

# Order Service (port 8080)
docker pull ghcr.io/<owner>/order-service:latest

# Or pin to an exact version using the Git commit SHA
docker pull ghcr.io/<owner>/order-service:abc1234
3
Run the container
Use -d to run in background, or remove -d to see live logs.
# Learning Service
docker run -d \
  --name learning-api \
  -p 8000:8000 \
  ghcr.io/<owner>/learning-service:latest

# Order Service
docker run -d \
  --name order-api \
  -p 8080:8080 \
  ghcr.io/<owner>/order-service:latest
4
Verify the service is healthy
# Learning Service
curl http://localhost:8000/health
# Expected: {"status":"healthy"}

# Order Service
curl http://localhost:8080/healthz
# Expected: {"status":"ok","service":"order-service"}

# Open Swagger interactive API docs in browser
# http://localhost:8000/docs   (Learning Service)
# http://localhost:8080/docs   (Order Service)
5
Rollback to a previous version
Because every pipeline run publishes an immutable SHA-tagged image, rolling back is a one-liner. Find the target SHA from the GitHub Actions run summary or GHCR package page.
# Stop and remove the current container
docker stop order-api && docker rm order-api

# Pull and run the previous known-good version by SHA
docker pull ghcr.io/<owner>/order-service:abc1234
docker run -d \
  --name order-api \
  -p 8080:8080 \
  ghcr.io/<owner>/order-service:abc1234
✅ Rollback is instant — the image is already in the registry. No re-build required.
6
Build & run services locally (without GHCR)
For local development, build and run directly from source:
# Build Learning Service from source
docker build -t learning-service:local services/learning_service
docker run -d --name learning-local -p 8000:8000 learning-service:local

# Run tests locally with coverage
cd services/learning_service
pytest --cov=app --cov-fail-under=80

# Cleanup
docker stop learning-local && docker rm learning-local
!
Common Issues & Fixes
Issue Likely Cause Fix
Coverage threshold failure Coverage below configured minimum Download coverage-report-{service} artifact → open index.html → write tests for red lines
Smoke test failure Container crashed or health route returned non-200 Check CI logs for Uvicorn tracebacks; verify port and health-endpoint inputs match Dockerfile EXPOSE
Port already allocated Host port in use by another container docker rm -f <container-name> then re-run
Registry casing error Uppercase chars in image name or owner OCI requires lowercase; pipeline auto-lowercases owner. Ensure image-name input is lowercase.
Ruff lint failure Style or import violations in source Run ruff check . locally in the service directory, fix issues, push again
Image not found in GHCR Pipeline ran on a PR (not main branch) Images are only published on pushes to main or release events — merge the PR first
